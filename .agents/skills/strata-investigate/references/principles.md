# 調査の共通原則

`docs/envvars/001_investigation.md`、`docs/cli/001_investigation.md`、`docs/cli/000_cli_tools.md`、
`docs/cli/README.md` の各所に書かれていた同じ原則を 1 本にまとめたもの。
**本文の正は上記 docs 側**にあり、ここに書いた要約と食い違ったら docs 側を正しいとして、このファイルを直す。

## 根拠の边界

- 事実の出典は、作業開始時点の Strata checkout（通常 `main` の HEAD）に含まれる **Strata 所有のソースコード**。
- 外部ライブラリ・GPU driver・Node や ROCm など同梱 runtime が読むだけの名前やフラグは、Strata の挙動として説明しない。Strata が値を読む／検証する／転送する／警告を出す事実だけを書く。
- 生成コード、ベンダーコピー、`third_party/`、`bench/results/`、`docs/`、`ref/` は実装根拠にしない（テストコードは候補値の手掛かりにだけ使い、本番コードで裏付けられない動作を断定しない）。
- 索引（`000_envvers.md`）と docs とコメントは「候補」であって仕様ではない。索引に載っていても、環境から値を読む箇所が見つからなければ環境変数として扱わない。
- 同じ名前でも backend・コマンド・parser が違えば別項目。統合するときは受理スコープと挙動が等しいことを確認してから統合する。

## revision と調査日

- 各セッションの最初に Strata 側で `git rev-parse HEAD` と `git status --short --branch` を取る。
- 成果物の先頭に `調査対象: Strata ... HEAD \`<40 桁 SHA>\`（YYYY-MM-DD 時点）` を書く（CLI 側は `調査対象: Strata commit \`<SHA>\`（YYYY-MM-DD 時点）`）。
- 異なる commit の調査を 1 文書に混在させない。tag と HEAD が同一コミットなら、Release とソースの対応の強い根拠になるので併記する。
- 作業ツリーに未コミット変更がある場合はそれを調査対象に含め、上書きしない。

## 推測の禁止

- 埋められない項目は空にせず「実体を確認できていない」旨を書く。特に Release 配布物・インストール先・プラットフォーム別の挙動。
- 値域・既定値・性能効果は、ソースに書いてある範囲だけを使う。速度向上の新たな推定・一般化はしない。測定値を書くときは資料の場所と測定条件（機種・OS・backend・モデル・量子化・設定・回数）を併記する。
- 索引との食い違い（候補なのに読み取り箇所が無い、option が現行 parser に無い）は、空の文書や別名の文書を作らず報告する。
- 「既定で ON/OFF」は、parse 結果（値が有効か）と有効条件（その機能が走るか）を分けて書く。値が有効でも条件不足で使われない経路を必ず書く。

## 編集の范围

- 1 セッションで編集するのは指定された 1 ファイルだけ。索引・`001_investigation.md`・他の個別文書・Strata ソースは変更しない。
- 作成先が既に存在する場合は上書きせず報告する。既存文書の更新を明示的に依頼された場合だけ書き換える。
- 索引更新のセッションでは、索引 1 ファイルだけを更新し、リンク先が未作成でも予定リンクとして列挙する（本文を作ったことにしない）。

## 実行してよいこと・だめなこと

- してよい: `rg` / `grep` / `git` / `python -c` での静的読解、安全に実行でき対象 checkout と同一 revision の CLI の `--help` 表示（補助情報。最終的に parser 定義と照合する）、GitHub Releases API や ghcr の tag 一覧取得、小さな Release asset のダウンロードと展開・ハッシュ照合。
- しない: Strata ソースの変更、build、GPU 実行、性能測定、テストの追加・実行（個別の依頼がある場合のみ例外）。
