# Strata CLI オプション調査手順

## 目的

Strata の CLI ツールとそのコマンドラインオプションを、ツール・コマンド・オプションの組み合わせごとに調査し、`docs/cli/` 以下に一意な Markdown 文書として記録する。調査対象となるツールの入口は [`000_cli_tools.md`](000_cli_tools.md) を起点にし、更新時は本書の手順に従う。

ここで作るのは、利用者が「どのツールの、どのコマンドのオプションか」「どんな値を指定でき、実行時に何が起こるか」を理解するための文書である。CLI の引数一覧を作る作業では、環境変数の文書を更新しない。

## 文書の一意な配置規約

### パス構造

オプション文書のパスは次の形にする。

```text
docs/cli/<tool-id>/<command-path>/<option-name>.md
```

- **`tool-id`** はツールの役割を識別する、固定の小文字 kebab-case 名とする。実行ファイル名だけでは識別しない。たとえば Terminal CLI とネイティブ推論エンジンはいずれも `strata` という名前になり得るため、`strata-terminal` と `strata-engine` のように分ける。
- **`command-path`** はサブコマンドの階層をディレクトリで表す。サブコマンドがないトップレベルの呼び出しには `root/` を使う。例: `launch/`、`bench/run/`。
- **`option-name`** は通常、オプションの正規の長い表記をそのまま使う。例: `--model.md`、`--help.md`。同じスコープ・同じ動作の短縮別名は一つの文書にまとめる。短い表記しかない場合は `-x.md` のようにする。
- `/` などファイル名に使えない文字を含むオプションは UTF-8 のパーセントエンコード表記を使う。エンコードは衝突しない一貫した規則で行い、文書内に元のオプション表記を必ず記載する。

例:

```text
docs/cli/README.md
docs/cli/strata-terminal/root/--help.md
docs/cli/strata-terminal/root/--version.md
docs/cli/strata-terminal/launch/--help.md
docs/cli/strata-terminal/launch/--model.md
docs/cli/strata-terminal/bench/run/--help.md
docs/cli/strata-engine/root/--help.md
docs/cli/strata-engine/root/--model.md
```

この規約では `strata --help` と `strata launch --help` は別文書となり、Terminal CLI とエンジンで同名オプションがあっても衝突しない。`root/` の `--help` はトップレベルのヘルプ、各コマンド下の `--help` はそのコマンド固有のヘルプを指す。

### ツール ID と委譲ラッパー

- ツール ID は一度決めたら、表示名・ファイル名・実装言語が変わっても同じ役割の間は維持する。役割が異なる実行プログラムは別 ID にする。
- 候補 ID は `000_cli_tools.md` の記載とソースを照合して決める。例: `strata-terminal`、`strata-engine`、`source-setup`、`quick-benchmark`、`release-installer-posix`、`release-installer-windows`。
- ラッパースクリプトが全引数を `setup.py` など別の実装へ渡すだけなら、オプション文書をラッパーごとに複製しない。実際のオプションを定義する CLI 側の文書に記載し、ラッパーの呼び出し方法と委譲先を説明する。ラッパー固有のオプションがある場合だけ、そのラッパーのツール ID で文書を作る。
- 同じオプション文字列でも、コマンドやツールによって値の解釈・既定値・副作用が異なる場合は別文書にする。反対に、短縮別名だけが異なり意味と適用範囲が同じなら一つにまとめる。
- 同一スコープで同じオプション文字列が複数 parser にある場合は、呼び出し文脈を特定できるコマンド階層で分ける。階層で区別できない場合は、追加のスコープ名をディレクトリに入れ、その理由を索引に記す。内容を推測して一つにまとめない。

### 索引

`docs/cli/README.md` を索引として作成・更新し、各ツール ID、その役割、文書化したコマンド、オプション文書へのリンクを掲載する。ツール一覧は `docs/cli/000_cli_tools.md` と一致させ、対象外にした入口（単なる build helper など）があれば、その分類理由を簡潔に説明する。文書を追加・削除・移動したときは索引も同期する。

## 調査対象と境界

- 調査対象は、調査開始時点の Strata リポジトリ checkout に含まれる Strata 所有のソースコードと、確認可能な公式 Release 配布物。文書に Strata の完全な commit SHA と調査日を書く。異なる commit の調査結果を一つの文書に混在させない。
- 対象は `000_cli_tools.md` に載るユーザー向け入口、ビルド生成される実行 CLI、Release で配布される CLI/installer とする。開発用ツール、診断コマンド、ベンチマーク用プログラムも、CLI として利用されるものは対象になり得るが、対象利用者・ビルド条件を明示する。
- `.sh`、`.bat`、`.ps1` 等の全てを自動的に CLI とみなさない。build 手順、CI 専用、テスト専用、個別実験スクリプトは、利用者向け入口かどうかを処理内容と文脈から判定する。
- 生成コード、依存ライブラリのオプション、GPU driver や外部ツールだけが読むフラグについては、Strata 自身の処理として説明しない。Strata が値を検証・変換・転送する場合は、その Strata 側の処理に限定して記述する。
- コメントや README に名前があるだけでは、現行 CLI オプションの根拠として不十分。parser 定義、引数転送、実際の使用箇所を確認する。現在使われていないオプションや互換目的で受理だけされるオプションは、その事実を区別して記載する。
- オプションの個別文書では、位置引数やサブコマンドの網羅を目的にしない。理解に必要な位置引数・関連サブコマンドは文脈として説明し、主題は一つのオプションに保つ。

## 調査手順

1. **対象 revision と作業状態を記録する。** Strata リポジトリで `git rev-parse HEAD`、`git status --short --branch`、必要に応じて `git log -1 --format='%h %cs %s'` を確認する。未コミット変更がある場合は内容を調査対象として扱い、上書きしない。
2. **CLI の入口・コマンド構造を把握する。** `000_cli_tools.md` の各対象を読み、実行ファイル名だけでなく実装ファイル、ラッパー、配布形態を確かめる。Python の `argparse`、C/C++ の引数解析、Node CLI、shell/PowerShell の引数処理、`package.json` の `bin` / scripts などを検索する。CLI ごとに `--help` 実装や subcommand 定義をたどり、オプションのスコープを作業メモに整理する。
3. **全オプションを列挙し、重複なく文書パスを決める。** `--help` 出力が利用でき、安全に実行できる既存バイナリまたは CLI がある場合は補助情報として参照してよい。ただし調査対象 checkout のソース定義と一致するか確認し、古いインストール済みバイナリを現行ソースの根拠にしない。help を安全に実行できない場合は実行せず、parser 定義・ソース・公式資料から列挙する。候補ごとに tool ID、command path、正規オプション名、別名を対応付け、既存ファイルと `docs/cli/README.md` を確認して重複・衝突を避ける。
4. **parser から実際の効果まで追跡する。** 各オプションの宣言、型変換、既定値、validation、分岐、呼び出し先、設定オブジェクト・実行計画・子プロセスへの転送を読み、必要に応じて全参照と helper の定義・呼び出しを検索する。宣言箇所で調査を止めず、値が最終的に何を変えるのかを確認する。
5. **値の規則・優先順位・副作用を調べる。** 省略時、明示値、空値、無効値、境界値、複数回指定時の扱いをソースで確認する。設定ファイルや環境変数と競合する場合の優先順位、他オプションとの相互作用、OS/backend/build/モデルによる有効条件、ファイル・ネットワーク・プロセス・server/GPU に対する副作用を追う。動的に更新可能か、起動時だけ読むかも分かる範囲で確認する。
6. **出力・失敗経路を調べる。** validation error、usage 表示、警告、終了コード、stdout/stderr、ファイル生成・上書き・削除などをコードで裏付ける。値が拒否・無視・補正される条件を通常経路と区別して説明する。
7. **利用者向け資料と Release を照合する。** README、`docs/`、packaging 資料、公式 Release 配布物など、現在の使い方の参考資料を確認し、ソース実装との不一致を区別する。最新 Release の実体を確認できないときは、その制約を明記し、ソース上の予定・生成規則を配布実績のように書かない。
8. **文書と索引を更新する。** 正しい `docs/cli/<tool-id>/<command-path>/<option-name>.md` に一オプションの文書を作り、`docs/cli/README.md` のリンクを同期する。既存文書がある場合は、同じ tool ID・command path・option identity か確認し、追記ではなく現行実装に合わせて見直す。廃止・改名された項目は索引と文書のリンク切れを確認し、履歴を残す必要があれば廃止状態を記して別の現行オプションと混同させない。

## 各オプション文書の内容

文書は日本語で書き、該当しない節は省略してよい。短いオプションでも、対象識別、利用例、値の規則、効果、適用条件、根拠を含める。

```markdown
# `--option`

調査対象: Strata commit `<完全な commit SHA>`（`YYYY-MM-DD` 時点）。

| 項目 | 内容 |
| --- | --- |
| ツール ID | `strata-terminal` |
| コマンド | `strata launch` |
| オプション | `--option` |
| 別名 | `-o`（なければ「なし」） |
| 値 | 値を取るか、形式・型・範囲 |

## 役割

このオプションが何を制御するか、どの利用者・実行経路で役立つか。

## 使い方

正確なコマンド例と、必要なら他オプションや位置引数を含む最小例。例がコード上の正式な構文と一致すること。

## 値と既定値

値の有無・形式・受理範囲、未指定時の既定値、空値・無効値・重複指定時の挙動。

## 実行時の動作

parser の受理から実際の効果まで。設定ファイル・環境変数・他オプションとの優先順位や相互作用も含める。

## 適用条件と副作用

OS/backend/build/モデル状態などの条件、無視・拒否・fallback 条件、ファイル・ネットワーク・プロセス・server/GPU 等への影響。

## 出力とエラー

確認できた stdout/stderr、警告・エラー、終了コード、失敗条件。該当しない場合は節を省略する。

## 根拠

主張の近くに `path/to/file.cpp:123` のようなソース位置を示す。関連する parser 定義、使用箇所、公式資料を区別して挙げる。
```

### 利用例の品質

- コマンド例にはツールとサブコマンドを必ず含め、どの環境・ディレクトリで使う例か必要な場合は記す。
- 機密情報を含む値、破壊的な出力先、既存ファイルを上書きする例を避ける。危険な副作用がオプションの主目的なら、動作を説明し、安全なサンプル値を選ぶ。
- 推奨値や性能効果は、ソースの動作説明と区別する。測定・推奨の根拠、機材、条件が確認できないなら「速くなる」などと断定しない。
- 環境変数との相互作用を説明するときは、対応する `docs/${環境変数名}.md` があればリンクする。変数の全仕様をオプション文書へ複製しない。
- 外部ツールやライブラリへオプションを転送する場合は、Strata がどの値をどう渡すかを主に記し、外部側の意味を説明するなら一次資料へのリンクを付けて境界を明確にする。

## 品質基準

- オプションの一意性は **tool ID + command path + option identity** で判断する。`--help.md` などファイル名単独で同一性を判断しない。
- 同じ正規オプションが異なるコマンドで異なる意味・値・既定値を持つなら必ず分ける。別名をまとめるのは、受理されるスコープと挙動が等しいと確認できた場合に限る。
- source checkout、ビルド生成バイナリ、Release archive、インストール済み wrapper の差を明示する。異なる backend や platform の差をひとつの値規則に押し込めない。
- 説明は parser の宣言だけでなく最終的な利用箇所まで追う。オプションが受理されても、条件により値が使われない、別値に補正される、後続処理に転送される場合は記述する。
- ソース・help・ドキュメント間に食い違いがある場合は、それぞれの根拠と対象バージョンを分けて示す。現行挙動を推測で埋めない。
- 引数 parser の範囲外である環境変数や外部依存の動作を、Strata CLI オプションの動作として混同しない。
- 調査目的で Strata ソースを変更しない。ユーザーから別途依頼されない限り、ビルド、GPU 実行、性能測定、テストを追加・実行しない。安全に利用可能な既存 CLI の help 表示は調査の補助として扱い、テストとは区別する。
- 調査できない backend、platform、Release artifact、値の境界があれば、その範囲を明記する。commit SHA と調査日を記録し、異なる commit の根拠を混ぜない。
