# Strata 環境変数の調査手順

## 目的

Strata の `main` にある環境変数を一つずつ調査し、本書の「文書フォーマット」と「詳しさの基準」に従って `${環境変数名}.md` を作成する。環境変数名の候補は `000_envvers.md` にある。各ファイルは、その名前の環境変数についてコードから確認できた事実を説明する。

書式と詳しさの基準は本書だけで完結させ、特定の既存文書を手本にしない。どの環境変数文書も他と同じ扱いで、陳腐化すれば削除して本書に従って作り直す。作業を複数エージェントに分ける場合は、各変数は一つの担当だけが書き、最終ファイル名と担当を共有して重複を避ける。

> 索引の再生成・削除・一括作成など作業全体の順序は、スキル `.agents/skills/strata-investigate/SKILL.md`（runbook）にまとめた。本書は環境変数 1 件を調べるときの仕様であり、リポジトリ運用の入口ではない。

## 調査対象と境界

- 調査対象は、作業開始時点の Strata リポジトリ `main` の HEAD に含まれる Strata 所有のソースコード。調査文書には HEAD の完全な commit SHA と調査日を書く。異なる commit の調査を一つの文書へ混在させない。
- 対象には Strata の C++/CUDA/HIP/SYCL 実装、Python サーバーやセットアップ、および候補一覧に含まれる Strata 同梱ツールを含める。
- 外部ライブラリや GPU ドライバー自身が読む環境変数の動作は説明対象外。Strata のソースがその変数を明示的に読んだり、設定有無を確認したりする場合は、Strata が行う処理（読み取り、分岐、警告、転送、値の設定など）だけを書く。外部ライブラリ側の意味を Strata の挙動として説明しない。
- `000_envvers.md` は grep で得た候補リストであり、その名前が通常利用者向け設定であることを保証しない。直接の実装箇所を見つけ、実行ファイルに組み込まれる機能か、開発・診断用フックか、同梱ツール専用かをコードで確かめる。
- 外部依存のソース、生成済みコード、ベンダーコピー、テスト専用コード、ベンチマーク結果・記録は環境変数の実装根拠にしない。リポジトリ内のテストは候補値を知る手掛かりにはなるが、本番コードで裏付けられない動作を断定する根拠にはしない。
- 文書だけに現れる名前、コメントだけに現れる名前、ビルド時の `#define`、コマンドライン引数名は、実際に環境から値を読むコードが確認できない限り環境変数として扱わない。

## 調査範囲

各変数について、次をソース全体で追う。

1. **読み取り箇所すべて**: `getenv` / `std::getenv`、Python の `os.environ.get` / 添字参照、共通の env helper、引数名を動的に渡す helper、プロセス起動時の読み取りを検索する。同じ名前の全参照を確認し、最初に見つかった箇所だけで判断しない。
2. **値の判定**: 未設定、空文字、一般的な値、無効な文字列、境界値、負値を含め、コードが受け付ける値を正確に書く。`atoi` / `atof` / `strtol` / `sscanf` / 文字列比較 / 先頭文字比較など、実際の変換方法を特定する。全体を parse するのか、先頭文字だけか、数値の後ろを無視するのか、大文字小文字を区別するのかを明記する。
3. **既定値と優先順位**: 未設定時の値、明示的な空文字の扱い、CLI 引数・設定ファイル・別の環境変数との優先順位、無効値時の fallback、clamp や範囲制限を特定する。複数の読み取り箇所で既定値が異なるなら、状況ごとに分ける。
4. **評価時期と適用範囲**: 起動時に一度読むか、初回呼び出し時に static cache するか、リクエストごとに読むかを調べる。プロセス起動後の変更が反映されるか、子プロセスへ継承・上書きされるかもコードにある場合だけ記述する。
5. **実際の挙動**: 変数の値がどの状態、計算、分岐、リソース、I/O、API 動作などを変えるかを、呼び出し元から結果が現れるところまで追う。値を読むだけの診断ログと実動作の制御を区別する。
6. **適用条件と相互作用**: OS、CUDA/HIP/SYCL、GPU 世代、ビルド macro、サーバーモード、CLI オプション、モデル状態、他の環境変数などの条件を列挙する。変数が有効値でも機能が使われない経路や、別機能により無視・上書き・fallback される経路を含める。
7. **観測できる結果**: stdout/stderr のログ、警告、エラー、終了・timeout、データ出力などを追える範囲で示す。文言を示す場合は実装上の文字列と一致させる。
8. **文書と測定値の照合**: `docs/DETAILS.md`、関連する設計資料や紙面を参照し、ソースコードとの一致を確かめる。性能値・正確性・token の同一性などは、Strata の資料に条件と測定環境が示されている場合だけ記載し、計測器の動作や資料中の主張を独自に確認した事実のように書かない。

## 手法

1. `git rev-parse HEAD` と `git status --short --branch` で調査対象の revision と作業ツリーを確認する。文書には `main` の HEAD SHA を記録する。
2. `rg -n --hidden --glob '!.git/**'` で環境変数名と env 読み取り API を検索する。対象は checkout 全体にし、除外は末尾一致で掛ける。例: `rg -n --hidden -g '!.git/**' -g '!**/third_party/**' -g '!**/docs/**' 'NAME|std::getenv|getenv|os\.environ|env_on|pipe_dbg_env|_timeout_env' "$STRATA"`。Strata の top-level 階層は Release で作り替わるので `src include sycl serve setup.py tools` のように階層名を並べた検索はしない（名指しした階層が消えても rg はエラーだけ出して進行する。extraction-recipes.md §1・§5）。候補名の完全一致検索に加え、汎用 helper と動的な名前の渡し先を調べる。
3. `000_envvers.md` の候補一つにつき、候補名を直接参照する全箇所を開く。`nl -ba <file> | sed -n '<start>,<end>p'` 等で実装と行番号を確認し、読み取り元から効果を及ぼすコードまで追跡する。関連する helper の定義だけで止めず、その helper の全呼び出し箇所も調べる。
4. 同じ名前が複数 backend やコピーされた CUDA/SYCL 実装にある場合は、各実装を比較して条件差があるか確認する。ビルド macro の分岐、platform guard、起動ラッパーから engine へ渡す環境も追う。
5. ソースの記述を既存 docs と照合する。食い違いがあればコード上の現状と docs の説明を分け、測定の不足や確認できない点を明記する。ソースにない値域や挙動を推測で埋めない。
6. 文書を対象フォルダーの `${環境変数名}.md` に保存する。環境変数一つにつき Markdown 一つ。`000_envvers.md` や Strata のソースコードは書き換えない。

## 文書フォーマット

文書は日本語で、次の見出し構成を基本にする。`## 役割`・`## 値と判定`・`## 有効になる条件`・`## 実行時の詳細` は必須（`check-docs.py` が検査する）。該当する内容が無い節も見出しは残し、「該当なし」とその理由を一文で書く。`## ログと測定値` は該当する場合だけ置き、対象変数に必要な節は追加してよい。

```markdown
# `ENV_NAME`

調査対象: Strata `main` の HEAD `<完全な commit SHA>`（`YYYY-MM-DD` 時点）。

## 役割

何を制御するか。通常の動作と比べて何が変わり、何は変わらないか。どの実行経路で効くか。実装の所在（関数名・ファイル）。

## 値と判定

読み取り方法（`getenv` の有無判定・先頭文字比較・`atoi` など）と、未設定・空文字・有効値・無効値・境界の規則。
build / platform などで判定が分かれるなら表にする。

| 条件（build など） | unset | 有効になる値（例） | 無効になる値（例） |
|---|---|---|---|

## 有効になる条件

値が有効でも機能が動くために必要な条件の箇条書き。満たさないときの扱い（無視・fallback・理由ログ）。

## 実行時の詳細

処理の流れ、読み取り時期と cache の有無、待ちや timeout、子プロセスやリクエストへの適用。

## ログと測定値

stderr / stdout の文言、Strata の資料に条件付きで記載された測定値（該当する場合のみ）。

## 根拠

`path/to/file.cpp:123-145` の形のソース位置。各節の主張の近くにも置く。
```

### 詳しさの基準

短い変数であっても、次をすべて満たす文書にする。単に `=1` を「有効」とするだけでは不十分である。

- **読み取り方法を特定する。** 文字列全体を parse するのか、先頭文字だけを比較するのか、設定有無だけを見るのかを書く。空文字が「設定あり」か「無効」かを明記する。
- **値の例を両側に挙げる。** 有効になる値と無効になる値を、境界になる具体例（`0`、`1`、`true`、`false`、空文字、`0anything` など）で示す。大文字小文字・空白・数値としての妥当性を検査するかどうかも書く。
- **既定値を条件ごとに分ける。** build・platform・backend・モード・CLI で既定値や判定が違う場合は、表で行を分ける。一つの値規則に押し込めない。
- **評価時期を書く。** 起動時に一度読む、関数内 `static` に保存する、リクエストごとに読む、のどれかと、実行中の変更が反映されるかを書く。
- **有効条件を列挙する。** 値が有効でも機能が動かない条件（他の CLI オプション、他の環境変数、GPU 構成、モデル状態など）を箇条書きで全部挙げる。他の環境変数は名前と必要な値まで書き、詳細はその変数の文書に任せる。
- **効果を結果まで追う。** 何の状態・計算・I/O が変わるかに加え、変わらないもの（生成 token、選択結果など）も、コードから言える範囲で書く。
- **観測手段を原文で書く。** 理由ログ・有効ログ・エラーの文言は、実装の文字列どおりに書く。ログが出ない条件（既定値のままのときに抑制される、など）も書く。
- **測定値は出典と条件つきで書く。** Strata の資料やソースコメントにある値だけを、機種・OS・backend・モデル・量子化・回数とともに引用し、一般化しない。資料とコードが食い違う場合は両方を分けて書く。
- **根拠を主張の近くに置く。** 節ごとに `path:line` を付ける。末尾の「根拠」節にまとめるだけにしない。

## 制約・品質基準

- 事実は調査対象 commit の Strata 所有ソースから導く。`000_envvers.md` の名前だけ、コメントだけ、過去バージョン、他プロジェクト、外部ライブラリの説明から現在の挙動を決めない。
- `getenv(...) != nullptr` は「値が `1`」を意味しない。空文字を含む設定有無の判定、文字列全体の比較、`atoi` の変換、先頭文字比較を混同しない。
- 「既定で ON/OFF」は設定値の parse 結果と実際の有効条件を分けて記述する。値が有効でも条件不足で機能が実行されない場合を必ず記す。
- コメントは設計意図や以前の測定を示す手掛かりとして扱い、実際の分岐と食い違う場合はコードを現行挙動の根拠にする。
- 測定値や速度向上を新たに推定・一般化しない。ハードウェア、OS/backend、モデル・量子化、設定、測定方法・回数が資料に書かれている場合は併記する。
- 外部ライブラリ・driver の内部動作を説明しない。Strata が値を読み、警告を出す場合はその事実だけを書く。
- 調査目的で Strata ソースを変更しない。ユーザーから別途依頼されない限り、build、GPU 実行、性能測定、テストを追加・実行しない。
- 複数の環境変数が相互作用する場合は、対象ファイルは主役の一変数に絞り、関係する変数名と必要条件を記載する。関連変数の完全な個別説明はそれぞれのファイルに置く。
- 根拠が見つからない、使われる条件がビルドできず確認できない、または複数の経路で意味が違う場合は、その制限を率直に書く。推測で断定せず、調査対象の commit SHA と対象範囲を明記する。
